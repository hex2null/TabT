# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A native macOS terminal emulator written in Rust on top of AppKit, built as a sequence of numbered milestones (step 0 = window, 1 = PTY echo, 2 = dumb rendering, 3 = VT parser). Steps 0–3 are done: it is a working multi-tab terminal with a self-drawn sidebar, groups, themes, fonts, settings, scrollback, and layout persistence. The sidebar reports live session state — running/idle/exited, unseen output, a rung bell, the shell's own title. Remaining known gap in the core: the scrollback is not reflowed on resize.

Keep new code comments and UI strings in English (the Rust sources are; the Makefile and `Cargo.toml` still carry some older Chinese comments).

## Commands

Run from the repository root (the workspace root — `Cargo.toml` and `Makefile` live here). The Makefile is the canonical entry point:

- `make test` — `tabt-core` unit tests (`cargo test -p tabt-core`; pure logic, runs on any platform) followed by `tabt-app`'s few (`cargo test -p tabt-app` — the `themes.conf` parser and the `layout.conf` `parse`/`render` round trip, macOS-only because the crate is).
- `make run` — build, bundle into `dist/TabT Dev.app`, codesign, kill any old dev instance, and `open` it. **The GUI must run as a `.app` bundle** — a bare `target/release/tabt` won't get focus or a menu bar (normal macOS behavior for non-bundled processes).
- `make release` — same, but with the shipping identity: `dist/TabT.app`, bundle id `dev.local.tabt`, config in `~/.tabt`. See "Build identities" below.
- `make echo` — the step-1 PTY echo loop (`cargo run --release --bin pty-echo`). **Must be run in a real terminal** (Terminal.app/iTerm); it calls `tcgetattr` on stdin and dies immediately without a tty (e.g. an IDE output panel).
- `make dmg` — build the release app, then `dist/TabT-<version>.dmg` (`bundle/make-dmg.sh`): the app plus an `/Applications` symlink in a compressed read-only image, the usual drag-to-install flow. Uses only system tools, and runs no Finder/AppleScript step: the window's icon size and layout ship as a pre-authored `.DS_Store` (`bundle/dmg-DS_Store`) that is copied into the image, regenerated by hand with `bash bundle/make-dmg-dsstore.sh` when the geometry or the item names change. The default image carries the local dev signature and is refused by Gatekeeper on other Macs; set `SIGN_ID` (Developer ID) and `NOTARY_PROFILE` (a `notarytool store-credentials` profile) to produce a shippable one. `dist/TabT.app` is **deleted** once it is inside the image — the `.dmg` is the deliverable, and a release bundle left in `dist/` is a second launchable copy of the *shipping* identity sitting next to the development one, sharing `~/.tabt` and the `tabt` process name with an installed TabT. Only on success, so a failed image leaves the bundle to inspect; `make release` still leaves it, which is what that target is for.
- `make cert` — one-time: create a stable local "TabT Dev" signing identity (`bundle/make-dev-cert.sh`). Without it `make run` falls back to ad-hoc signing, which changes the app's designated requirement on every rebuild, so macOS re-prompts for TCC folder access each time.
- `make bloat` — size audit (`cargo bloat`, needs `cargo install cargo-bloat`); the stripped binary should be ~1 MB.
- Single test: `cargo test -p tabt-core <test_name>` (e.g. `cargo test -p tabt-core print_and_wrap`).

There is no separate lint step (no clippy/fmt target).

The release profile is aggressively size-tuned (`opt-level="z"`, `lto`, `codegen-units=1`, `panic="abort"`, `strip`). `panic="abort"` means a panic anywhere terminates the whole process rather than unwinding — relevant when touching code that parses PTY output or user input.

## Architecture

Two-crate Cargo workspace with a strict dependency direction: `tabt-app` → `tabt-core`, never the reverse.

### `tabt-core` — the VT/ANSI engine

`tabt-core/src/lib.rs`, one file, **deliberately zero-dependency** so it compiles and tests on any platform independent of macOS. Defines `Cell`, `Color`, and `Grid` (fixed-size screen grid in a flat `Vec<Cell>`, indexed `row * cols + col`).

`Grid::feed(&[u8])` is a VT500-style parser state machine (ground / escape / csi / osc, modeled on Paul Williams' diagram) covering SGR pen attributes, cursor movement, erase/insert/delete, scroll regions, save/restore cursor, DEC private modes, IRM, alternate screen, tab stops (a per-column table, edited by HTS/TBC and walked by CHT/CBT), the DEC Special Graphics charset, OSC title and OSC 7 cwd, UTF-8 and wide characters (a wide glyph occupies two cells, the second flagged `WIDE_TRAILER`). Terminal→host replies (DSR/DA) are queued internally and drained by the app layer via `take_replies()`; other state the renderer/input layer reads back through `cwd()`, `title()`, `cursor_visible()`, `app_cursor_keys()`, `bracketed_paste()`, `mouse_mode()`. `take_bell()` **consumes** rather than peeks, because the mark it feeds is cleared by being seen. Note the BEL that terminates an OSC string is eaten by the OSC state and never reaches `execute`, so setting a title cannot ring the bell — there is a test pinning exactly that, since otherwise a title-setting prompt would mark its tab on every command.

Lines scrolled off the top are pushed into a capped `history` deque. **The renderer must read cells through `view_cell()`, not `cell()`** — `view_cell()` resolves the current scrollback viewport (`view_offset()`, moved by `scroll_view()` / `scroll_to_bottom()`); `cell()` is raw screen access. The alt screen has no scrollback, and lines removed by DL/ED must not enter it. `to_lines()` exports rows as trimmed strings, used by the ~40 unit tests at the bottom of the same file; `buf_text()` is the same idea over the *whole* buffer (history first, then the screen, trailing blank rows dropped) and is what Shell → Export Text writes to disk.

### `tabt-app` — the macOS/AppKit layer

Two binaries:

- **`src/main.rs` (bin `tabt`)** — process setup and window/layout construction only. Sets `TERM`/`TERM_PROGRAM` env *before* AppKit starts any thread so forked children inherit a clean env (see the comment there about Apple_Terminal's `~/.zsh_sessions` clash). Builds the container view (sidebar | divider | terminal host | floating toggle), then hands off to `AppController`.
- **`src/bin/pty_echo.rs` (bin `pty-echo`)** — a self-contained PTY loop using **raw `libc`**, no AppKit. It exercises the low-level PTY details (`setsid`, controlling terminal, fd inheritance, raw mode, `SIGWINCH`) that were later lifted into the GUI. Kept permanently as a debugging tool.

**Everything runs on the main thread**, enforced at the type level via `MainThreadMarker`. All custom views are `NSView` subclasses declared with `objc2`'s `declare_class!`.

#### The controller / callback pattern (read `app.rs` first)

`AppController` (`app.rs`) is a plain Rust struct in an `Rc`, created in `main()` and kept alive until `app.run()` returns. It owns every session (each tab = one PTY fd + one `TermView` + a shell pid + a GCD reader token) and handles create/switch/move/close/rename, sidebar layout, theme/font changes, and persistence.

Because ObjC objects can't hold Rust `Rc`s, the sidebar, divider, toggle, menu target, and settings dialog each store a **raw `*const AppController`** and call back through it (plus `extern "C"` trampolines for GCD callbacks). This is sound only because the `Rc` outlives the event loop — preserve that invariant when adding a new view. There is intentionally no reference cycle: the controller owns the views, the views only point back.

#### Data flow

Background **fills** (the terminal's default background, the header/placeholder behind it, the card, the window's own color) go through `view::ns_color_bg`, which carries the opacity setting; everything drawn on top — glyphs, the card hairline, a cell's explicit SGR background — uses `ns_color` and stays opaque, which is what keeps a translucent window readable. `sync_window_chrome` flips `setOpaque:` to agree. Nothing touches `NSWindow::setAlphaValue`, which would fade the text with it.

The cursor blink is a **GCD timer source** owned by `AppController` (`view::attach_timer`), not an `NSTimer`: the controller is a plain Rust struct and cannot be an ObjC target, and making a `TermView` the target instead would have the timer retain a view the controller must be free to drop. One timer for the app, since only the active view is mounted.

**Session state** — whether a tab is `Running` (a foreground job other than the shell owns the terminal), `Idle` (at a prompt) or `Ended` — is *sampled*, by a second GCD timer (`sample_states`, `SAMPLE_MS`). It cannot be computed on demand: `Running` comes from a `tcgetpgrp` syscall and the sidebar redraws on a hovered row and on every keystroke that edits a title. Three rules hold:

- **The sampler redraws only when a state actually moved.** An unconditional refresh is a permanent 1 Hz repaint of the whole sidebar, worse than the wrong dot it fixes.
- It is a **separate timer from the blink**, which only exists while Settings → Terminal → Blink is on — and that is off by default, so there is frequently no timer to share. This one lives as long as the controller, so no teardown path can leave it firing on dropped state.
- `end_tab_session` and `restart_tab` set the state *and* refresh themselves, rather than waiting up to a sample. Because they set it directly the sampler then sees no change, so anything that must follow a state change — `refresh_sidebar`, `update_header` — has to be called from them explicitly. Both scope their model borrow first, since those calls take it again.

A tab's label and icon take their tier from **selection alone**. Unseen output marks the row with a dot at its trailing edge instead: a row's brightness is a fact about the list — which one you are in — and letting output raise it left every row that had printed anything at full weight until it was visited, with that contrast gone. Two more marks ride along: **activity** (a background session printed something unseen — a counter on `TermView` bumped per read, compared by the sampler, so the PTY path has nothing to clear; a tab's *first* reading only establishes the baseline, or a restored layout would mark every tab in it on the first sample, the shells' own prompts arriving after `select` had resynced only the active one) and **bell** (`Grid::take_bell`, drained every sample whether or not it is used, or it would latch and fire the next time the tab went background). Both are cleared by selecting the tab, which also resyncs `last_seq` — otherwise output produced while it was in the background re-marks it on the next tick.

The **status dot** draws from two independent axes, which is what lets it carry the user's colors and the session's state at once without a precedence rule: **hue** is the user's (an explicit `dot` index is drawn as chosen; only a default-colored tab takes green/neutral from the state) and **form** is the session's (solid running, dimmed idle, hollow ring ended). Selection deliberately does **not** touch it — that it used to is why green meant "the tab you are looking at" rather than "running". The ring is placed on whole/half points or it smudges across two device pixels.

A read that changed the grid's **title or cwd** additionally fires `TermView`'s `meta` callback (the fourth trampoline on `attach`, alongside end/restart/toggle), which is what keeps the sidebar row and the header's meta line current. It compares borrowed `&str`s against the last values reported, so a read that moved neither — nearly all of them — allocates nothing.

PTY master fd → GCD dispatch source (`view.rs`, hand-declared `dispatch_*` externs) → `Grid::feed` → `setNeedsDisplay` → `drawRect:` merges runs of adjacent cells with identical attributes and draws each run once with Core Text (backgrounds/underlines via `NSRectFill`). `keyDown:`/`NSTextInputClient` write back to the fd; `take_replies()` output is written back after each feed; `scrollWheel:` moves the scrollback viewport instead — except on the alternate screen, which has no scrollback: there `Grid::alt_scroll_keys` turns the wheel into cursor-key presses (xterm alternate scroll, DECSET 1007) so the full-screen application scrolls itself. Mouse selection is stored in virtual-buffer rows (`Grid::buf_cell`), not viewport rows, so the highlight stays on its text while the viewport moves. A window/font/sidebar resize recomputes cols/rows from the cell metrics, reflows the grid, and notifies the shell with `TIOCSWINSZ`.

The mouse has **two possible owners**, and every event has to be routed between them (`view.rs`, `mouse_owned_by_app`). An application that asked for tracking (DECSET 1000/1002/1003) gets the event encoded by `Grid::mouse_report_bytes`; otherwise it drives the terminal's own text selection. Three rules are load-bearing and each is easy to get wrong:

- Motion is gated on `mouse_mode() >= MouseMode::Drag`, not on tracking being on at all. Mode 1000 asks for presses and reports no motion, so treating it as a blanket grab would leave a drag doing nothing in either direction.
- Once a press has been taken, the rest of that gesture belongs to the application even if its mode discards the motion — otherwise the drag falls through and extends a selection against an anchor this gesture never set, i.e. from wherever the *previous* selection began. The gesture ends at the button-up, so the release is reported on the strength of the remembered press alone (`mouse_held`): re-testing ownership there would swallow it whenever the user pressed Shift mid-drag, leaving the application with a button it thinks is still down. Buttons chord, so the list holds every held button and each release names its own.
- Holding **Shift** always hands the mouse back to the terminal (the xterm/iTerm2 convention; without it there is no way to select text under tmux or vim), and so does a scrolled-back viewport, whose rows are history the application never drew and whose coordinates would therefore name the wrong line.

Motion reports are deduplicated by cell, since AppKit delivers motion per pixel and the protocol has no sub-cell resolution. Mode 1003's button-less motion is the only reason `TermView` installs an `NSTrackingArea`. Tracking also takes the wheel — an application that asked for the mouse gets button 64/65 reports rather than synthesized cursor keys — but that decision belongs to `scroll_wheel`, not to `alt_scroll_keys`, which knows nothing about tracking: on the alternate screen the Shift escape hatch has nowhere to go but those cursor keys, since there is no scrollback to move. A press taken by the application still clears any leftover selection, which otherwise stays painted over the application's UI and keeps being what ⌘C copies.

`pty.rs` spawns each tab's login shell (`openpty` + `fork` + `setsid` + `TIOCSCTTY` + `execv`), returns a non-blocking master fd, and installs a one-time `SIGCHLD` reaper. Which shell: the Settings → Shell value, else `$SHELL`, else `/bin/zsh`; argv[0] is the basename with a `-` prefix, which is what makes it a login shell. A *configured* shell that isn't executable fails the tab (and raises the caller's alert) rather than falling back silently, because that is a mistake the user can see and fix; an unusable `$SHELL`, which they did not choose here, does fall back. A spawn failure must fail only that tab, never the app. `has_foreground_job()` compares `tcgetpgrp` against the shell pid to warn before closing a tab with a running job. A shell that exits does **not** close its tab: the session is marked ended, `TermView` shows a placeholder, and Enter respawns into the tab's last cwd (`AppController::restart_tab`). `restart_tab` is only correct for a session that has *already* ended — it overwrites `master_fd` and the reader token without closing either — so the toolbar's Restart button (`restart_active_tab`) takes a live one down first: confirm if there is a foreground job, `SIGHUP` the shell's process group (it is its own session leader, so the negated pid names the group), then the same teardown `end_tab_session` does, and only then respawn.

#### Views and state

The sidebar, header, divider, toggle, placeholder and the theme picker are **all self-drawn** (custom `drawRect:`, own hit-testing and drag handling) — the settings dialog (`settings_dialog.rs`) is otherwise the lone user of standard AppKit controls. It holds five panes (Theme / Appearance / Toolbar / Terminal / Shell) in an `NSTabView` set to `NSNoTabsNoBorder` — no tab strip, no box around the content — switched by an `NSSegmentedControl` above it. Rows are placed by `Rows`, a cursor stepping one `ROW_H` at a time, so a new setting is one `rows.next()`; the two numeric ones (font size, padding) are sliders over the range the app accepts, continuous so the terminal follows the drag, rounded in the action and applied only when the whole-point value actually moves — every apply reflows every tab's grid and re-sends `TIOCSWINSZ`, which is not something to do per pixel of travel; every pane is the same height (`PANE_H`, set by what the theme grid wants) and the panel's width is the Toolbar pane's (a 1:1 title bar, see below) so switching never resizes the window, and every pane's first row starts at the same top edge. Esc closes it, through a hidden zero-size `NSButton` carrying that key equivalent rather than a `cancelOperation:` responder method — this is a plain window, so that method only reaches whatever control has the keyboard and a text field swallows it; the button's action goes through `performClose:` so `windowWillClose:` still commits the shell field. The panel deliberately sets **no** appearance of its own: unlike the terminal window, whose chrome is the theme's (`sync_window_chrome`), it is a system panel and follows the system's light/dark setting — the theme is previewed *inside* it, on the Theme pane's cards, not applied to it.

The Theme pane is `theme_grid.rs`: a `ThemeGrid` in an `NSScrollView`, one card per registry entry, each card a **miniature of the app in that theme** — its terminal background, a recessed sidebar in `card_bg` with three row bars, three lines of prompt/listing/cursor in the theme's own palette, then the name and six ANSI chips. It is the picker precisely because a name in a pop-up says nothing about a color scheme. The grid reads `theme::names()`/`by_index` and calls `AppController::set_style`; the dialog only pushes the selection back in (`set_selected`) when it re-seeds. It scrolls because `themes.conf` is user-editable and can hold any number of themes. Like the main window it pins its appearance to `theme::current().is_dark()`, and `sync_window_chrome` re-applies that on every theme change — half the shipped themes are light, and a hard-coded `NSAppearanceNameDarkAqua` (what it used to do) puts dark controls on a light window.

The sidebar is a **floating card**: `card.rs` wraps `SidebarView` in a layer-backed `NSView` inset `CARD_INSET` from the window edges and separated from the terminal by `CARD_GAP`, with the fill, hairline border and corner radius all living on that layer. Three things follow from that and are each easy to break:

- `SidebarView::render` must **not** fill a background, or it covers the card's fill and its rounded corners.
- The card's corners are **concentric with the window's**, which means two things and not one: the radius is `WINDOW_RADIUS − CARD_INSET` (the window's own is ~26pt, measured off a screenshot — there is no API that answers it — so an inset shape needs the difference, not the same number), *and* the curve is continuous rather than circular (`setCornerCurve:`), because at an equal radius the two shapes still part company visibly, the circular one turning sooner and flatter.
- The terminal and the gutter around the card are the plain theme background; the card is that background stepped one notch deeper (`Theme::card_bg`, a fixed *perceived* luminance step so it lands the same on a near-black theme and a white one), so the panel reads as its own recessed surface and the hairline is left much fainter than the step. A wide, very faint drop shadow then lifts the card off the gutter; keep it near the limit of visibility, because a heavier one tints the CARD_GAP gutter it falls into and that gutter is shared with the terminal, so it becomes a dark seam down the middle of the window. A layer's shadow is drawn outside its bounds, so the card layer must stay **unmasked** — the rounded clip lives on the *content* layer (`card::new`), which has the card's exact frame; putting `masksToBounds` back on the card silently erases the shadow.
- Layer colors are concrete, so `sync_window_chrome` must call `card::apply_theme` on every theme change; unlike the `drawRect:` views the card cannot re-read the theme itself.

The top strip is arranged like the system's sidebar apps: traffic lights at the sidebar's top-left, its search and collapse buttons at the far end of that same strip (`toggle.rs`, one `StripButton` class in two roles), session title at the terminal's own left edge (`header.rs` spans the host, not the window). The band is a real **`NSToolbar`** (`toolbar.rs`) over a transparent, full-size title bar: the toolbar owns the row, so `titlebar_center_y()` follows *it* (`band_h() / 2`, the band read back off `contentLayoutRect` rather than assumed — with a toolbar attached that height is the system's, and `HEADER_H` is only the fallback), and everything else is placed onto that line. `header.rs` is what paints the band in the theme's background and draws the title on it; the toolbar contributes only the button.

Dropping a dragged tab shows one of two things, never both: the **insertion line** between two rows, or — when the pointer is over a *collapsed* group — a **container highlight** on that group's row, because a collapsed group has no visible gap for a line to mean anything in and the line under its title reads as "after this group" rather than "into it". The drop itself needed nothing: a group row has always resolved to that group's region, and with none of its tabs on screen the insertion lands at its end. The highlight is suppressed during a search, where a collapsed group's matches *are* listed underneath it.

The **search box is not in the sidebar at rest**: `build_rows` only emits its row while the search actually has the keyboard *or is still animating*, so the session list starts right under the top strip and the box is reached through the strip's magnifier or ⌘F. Everything that measures the fixed area therefore has to ask `search_h()` rather than assume a permanent row — `list_top`, `build_rows` and `max_scroll_of` became `&self` methods for exactly that, and being one row off there draws the list into the clip of the row above it. The ⌘F hint the box used to carry on its own face moved to the magnifier's tooltip, since a box you cannot see cannot advertise anything.

⌘F opens it, and — while it is open and still **empty** — closes it again; with a query typed in, ⌘F leaves it alone, because that text is the user's work and Esc is where they would expect to discard it. **Losing the keyboard does not close it**: click into the terminal and the box stays, still filtering, so a filtered list survives going back to work. Only Esc, ⌘F on an empty box, and the magnifier close it. That splits one question into two — "the search is on" (`searching`, which draws the box) and "the search has the keyboard" (`has_keyboard`, which draws the ring, the caret and the `esc` hint, since none of those mean anything while the keys are going to the terminal). Collapsing the sidebar keeps the box but hands the keyboard back, or a card parked off the window edge would swallow everything typed at the terminal. Opening and closing it is **animated** (`SEARCH_ANIM`, a GCD timer the sidebar owns and cancels on arrival — `reveal` is where the box *is*, `searching` where it is going, and they disagree for exactly as long as the motion lasts). The box is drawn at full size and clipped to the unrolled height, so it opens like a drawer rather than squashing its text through a vertical scale; the row's `h` is that same clipped height, so hit testing follows what is on screen. The focus ring is stroked half a point *inside* the box, because a stroke is centered on its path and the reveal clip would otherwise cut its top and bottom edges off.

Which buttons appear, and in which order, is **Settings → Toolbar** — a customizer (`toolbar_editor.rs`) rather than a column of checkboxes, on the same argument the theme grid replaced the theme pop-up on: it draws the thing being chosen. It draws **one editable row per group**, AI then Common, and every button in them at the size the window gives it: the theme's background behind it, the icon at `ICON_PT` in `Toolbar`'s own tone, a 44pt item box, items abutting, and the capsule recent macOS draws behind a run. Those metrics are measured off a live window's item views (`NSToolbarItemViewer` frames), because AppKit answers none of them, and they are what set the settings panel's width and height. It is deliberately **not** a picture of the whole title bar: the traffic lights and session title were drawn here for realism and cost the rows most of their width for nothing an editor needs. A run still outgrows a pane far narrower than a window, so a row **clips** its own contents and marks the cut with an ellipsis rather than painting over the pane — the real toolbar has the whole window and hands its own overflow to AppKit.

**The row a button sits in is its group.** `Group::Ai` and `Group::Common` are one capsule each, in that order, and dragging a button across the gap between the customizer's rows moves it between them — `Entry::group` is only where a button *starts*, the row it joins the first time it is placed. That is also why there is no draggable Space tile any more: the break between the capsules is the break between the rows, and a button that could be dropped either side of it would say the same thing twice.

**Two keys back it, and neither is redundant.** `toolbar_hidden` is the visibility, stored as the *hidden* set so a button a later version adds shows up rather than staying invisible on an existing config; `toolbar_order` is the arrangement, and a shown button it does not mention — exactly that newly added one — is appended in `CUSTOMIZABLE`'s own order rather than dropped. `toolbar::rows()` resolves the two into the pair of rows, and is what both the customizer and `identifiers()` build from. `Entry::default_on` is the **one deliberate exception** to that appending rule: a version adding seven buttons at once would otherwise rearrange a bar the user had arranged by hand, so the newer ones (the three extra AI launchers, interrupt, restart, and the font pair) start in the palette instead — one drag away, and impossible to miss there, since the palette is what the pane is mostly made of. It applies **only** to appending: a button the user dragged in is honored from the stored order regardless, and `toolbar::defaults()` is what Restore Defaults goes back to, so "restore" cannot drag in what the table keeps out. `SPACE_KEY` survives as the **divider token** in that one stored list — keys before it are the AI row, keys after it the Common row — which is what lets the two rows and the toolbar's own item sequence be the same list written once, and what lets a config written when the space *was* a button read back unchanged. A list with no divider at all (older, or hand-edited) is read back into the rows each button's table entry names, keeping their relative order, so an arrangement never collapses into one row on upgrade; and the divider is dropped from the toolbar itself when either row is empty, since a space at either end is a gap with nothing on one side. The drag itself commits **once, on mouse-up** — `Toolbar::rebuild` removes and re-inserts every item, which is not a per-frame operation — and a press that never moves does nothing at all, or a stray click outside a row would read as "remove".

The toolbar's **trailing group** holds, out of the box: `claude` and `codex` (which type their command into the session and press Return — the shell resolves the name, exactly as the user would; `gemini`, `aider` and `cursor-agent` are the same mechanism, waiting in the customizer's palette), then home, copy, paste, clear line, clear, screenshot, and a share button (`square.and.arrow.up`) that drops a menu with Export Text and Reveal in Finder — an `NSMenuToolbarItem`, which is the class for a button that opens something rather than firing, and draws the chevron that says so. Each sends the selector its menu item already sends, so the two routes cannot drift; `copy:`/`paste:` are deliberately left **targetless**, because they belong to whichever `TermView` has the keyboard (a fixed target would send them to an object that does not implement them, and the buttons would validate as disabled). **Clear is a `⌃L` written to the PTY**, not an `\e[2J\e[H` fed to the grid: wiping the grid leaves the shell believing its prompt is still on screen, so the line vanishes and nothing comes back until the next Return — `^L` has the shell repaint its prompt, and a full-screen application redraw itself. **Interrupt is the same idea**: a `⌃C` written to the shell, because the tty driver is what turns that byte into SIGINT for the *foreground* process group — the one the user means, and the one this side cannot name.

Icon **tone and size are the theme's, not the system's**: a symbol image baked with a hierarchical color configuration at `ICON_DIM` from the foreground and `ICON_PT` point size, because AppKit tints a *template* image in its own control color and sizes a toolbar symbol larger than the card's own strip buttons — side by side in one row, either difference shows. A baked image holds a concrete color, so `sync_window_chrome` re-applies it on every theme change (`Toolbar::apply_theme`), exactly as it does for the card's layer.

**Search and collapse exist twice, on purpose.** Expanded, the pair on screen is the card's own (`toggle.rs`, one `StripButton` class in two roles), self-drawn at the card's top-right — they ride the card, so `relayout` parks them off the window edge with it and a collapse slides them away instead of blinking them out. Collapsed there is no card to carry anything, so the toolbar's pair takes over between the traffic lights and the title, in the same order the strip used. They swap in `relayout` via `Toolbar::set_shown`, which **removes and re-inserts the items** — `NSToolbarItem` has no setter for `isVisible` — and that happens once per collapse, not per frame. Both sets send the same selectors the View menu does (`toggleSidebar:` / `findSession:`), so no route can reach a state another cannot.

Three further things about that toolbar are the result of measurement, not documentation, and each cost a rewrite:

- The button is **not** `NSToolbarToggleSidebarItemIdentifier`. That reserved item wants a window whose content view controller is an `NSSplitViewController`; with a floating card AppKit resolves no target for it and ships it permanently disabled, without ever calling `validateToolbarItem:`. What is there instead is a plain bordered image item carrying the system's own `sidebar.left` symbol — the same button to look at and to click — pointed at `MenuTarget`'s `toggleSidebar:`, the selector the View menu already used. The target is set **explicitly** (`AppController::set_toolbar_target`, from `main` once that object exists): `MenuTarget` is only the window's *delegate*, and an item whose target the responder chain cannot resolve is drawn disabled.
- **The session title is not a toolbar item.** It has to start at the terminal's left edge, which moves with the sidebar, and AppKit measures a custom item view exactly once — when the item is inserted. `minSize`/`maxSize`, `invalidateIntrinsicContentSize` and `setNeedsLayout` up the chain all leave it where it was first placed, so a title item could be positioned but never re-positioned. `HeaderView` spans exactly the terminal pane, so it gets that alignment for nothing.
- Sizing a custom item view at all is `setMinSize`/`setMaxSize` **or nothing**: with constraints or an `intrinsicContentSize` alone the item reports itself visible, its frame reads correctly, and `drawRect:` is simply never called.

The lights are additionally shifted right by `CARD_INSET` — AppKit positions them against the *window*, so without that they sit hard against the card's rounded corner instead of the standard distance from the edge you actually see. Their baseline x is captured once (`light_x0`) rather than offset in place, because `reposition_traffic_lights` can run when AppKit has not reset the frames and a relative shift would accumulate. **`setTitle:` puts the lights back at AppKit's own coordinates, synchronously**, so `update_title` re-centers them inline right after — deferring that to the next run loop turn (as it once did) lets the window flush in between and the buttons visibly jump on every tab switch. For the same reason `update_title` skips the call when the string has not changed, and the header's meta line (the session's directory and shell, `update_header`) is updated **separately**: it changes on every `cd`, and routing that through `setTitle:` would relay out the title bar each time. Collapsed, the title's inset grows past `TOGGLE_RIGHT_X` — where AppKit puts the toolbar's button, measured off a screenshot rather than derived, since that position is the system's — to clear both it and the lights. Expanded it is a plain `TITLE_INSET` from the terminal's edge, except with the sidebar docked right, where the lights are over the terminal and it has to clear those instead.

`CARD_INSET`/`CARD_GAP` also define where the divider sits and how a divider drag maps back to a width — change one and `drag_sidebar_width` has to follow. Collapsing does not hide the card: `relayout` parks it just past the window edge, and `toggle_sidebar` slides it there through `NSAnimationContext` (`set_frame_maybe_animated`). Only the card and its toggle animate — animating the host would reflow the grid and `TIOCSWINSZ` the shell on every frame of the slide.

⌘~ (⇧⌘`, "Last Session") flips to the session that was active before this one, and again to come back: `select` records the outgoing tab whenever the selection actually moves, so the two ping-pong. It is silent when there is nothing to return to or that tab has since been closed.

Two sidebar actions are reachable from the keyboard through the menu and need the row on screen first: ⌃↩ (context menu) and ⌘R (rename in place). Both go through `SidebarView::reveal_active_row`, which expands a collapsed group, scrolls the row into the visible band and **flushes** the redraw — `popUpMenuPositioning…` runs its own modal loop, so a merely invalidated view would still show the pre-scroll rows under the menu. ⌃↩ prefers the row under the pointer; ⌘R deliberately does not, since a rename landing on whatever the mouse rests over would be a nasty surprise.

`menu.rs` sets `MenuTarget` as every submenu's delegate purely to strip the SF Symbols recent macOS attaches to standard menu items; the images are applied at display time, so clearing them at build time does not stick.

`theme.rs` and `settings.rs` hold main-thread-only global state that the drawing code reads on demand, so views don't depend on each other: the current theme in one, and in the other everything the settings dialog can change — font family/size and derived cell metrics, cursor shape/blink (plus the blink *phase*, which the controller's timer flips and typing/output forces back to visible), content padding, background opacity, scrollback depth, the shell and where a new tab starts. Enumerated ones (`CursorShape`, `NewTabDir`) own their persisted `name()`.

`config.rs` persists layout to `~/.tabt/layout.conf` (`~/.tabt-dev` for dev builds, see `branding.rs`) in **hand-written INI** (no serde, to keep the binary small); values are unescaped, so a label must never contain a newline. Both label sources go through `config::sanitize_label` — the rename box and, since titles can now arrive from the shell, the OSC title, which may come from a remote host over ssh. It truncates by **characters, never bytes**: the OSC payload is bytes through `from_utf8_lossy`, and byte-slicing one mid-character panics, which under `panic = "abort"` is the whole app. The format is `parse`/`render`, with `load`/`save` only `fs` around them — the split is what makes it testable, since `load()` reads a path under `$HOME` and a test written against it would clobber the developer's own config. The window's **position** is persisted alongside its size, and the two need different "unset" markers: the size uses `0`, which cannot be a real width, but `0` *is* a real coordinate and so is a negative one (a display above or left of the main one), so `window_x`/`window_y` are `Option`s written only when present — an absent key means "center it", which is what every config written before they existed says. `main` therefore calls `AppController::place_window` instead of `center()`; macOS's own restoration stays off (`setRestorable: false` would override the contentRect), and a restored origin is only trusted when `NSWindow::screen` still answers — a display can be unplugged between runs, and a frame intersecting nothing puts the window where it cannot be reached. The origin is read at save time rather than tracked, because `windowDidMove:` fires per frame of a drag and each save rewrites the whole file. Everything in `[settings]` travels as one `Settings` struct. Two rules hold for every key: unknown keys and sections are ignored (so a newer version's config stays readable and no migration step is ever needed), and enumerated values are stored **by name**, never by index.

A tab's name follows a chain: a ⌘R rename wins permanently, else the shell's OSC 0/1/2 title, else the directory it sits in. The middle rung is rarer than it sounds — `/etc/zshrc` only sources a title-setting hook for `Apple_Terminal` and `main.rs` deliberately reports `TERM_PROGRAM=TabT`, so a stock zsh here never sets one; OSC titles are what ssh, tmux and vim contribute on top. Which kind a stored title is travels as **`auto = true`, written only for the derived case, so an absent key means pinned**. That inversion is the point: every config written before the key existed keeps its titles, which is the only behavior that cannot silently discard a rename. `tab = ` is still written for every tab, derived or not, so a restored session reads correctly before any shell has reported anything.

The themes are **data, not source**, and their one home is `bundle/themes.conf` — installed read-only into the app bundle (`Contents/Resources/themes.conf`) and copied verbatim to `~/.tabt/themes.conf` on first run. `theme.rs` compiles in a single theme, `DEFAULT_THEME`, which is *not* the theme the app starts on but the base a parsed `[theme]` inherits each unset field from, plus the one-entry registry left if no file can be read at all; everything else — the settings pop-up, the saved `style` name — goes through the runtime registry (`names()` / `by_index()` / `index_of()`, filled lazily on first use so no ordering against `config::load()` has to be maintained). `ensure_loaded` tries the user copy, then the bundled one, then that base. Four consequences: adding or editing a theme means editing `bundle/themes.conf` (the `shipped_file_parses` test is what guards it — a typo there ships an app with one theme, and the lenient parser will not complain); the user copy is **authoritative** when present, so a shipped theme it omits is gone (its *order* is not the pop-up's — `ensure_loaded` sorts the registry by name, so the file is free to be grouped however reads best), at the price of a theme added by a later version not reaching a copy seeded by an earlier one; the app **only ever reads** it and seeds it only when it is absent (unlike `layout.conf`, which `config::save` rewrites wholesale — hand-written themes there would be dropped by the first save that didn't model them; and a user copy that fails to parse is still the user's, so it is left alone rather than replaced); and parsing must stay lenient, since `panic = "abort"` turns one bad line in a hand-edited file into a dead app. `style` is stored by name, never by index, so adding or reordering themes cannot repoint an existing config. An unbundled `cargo build` binary has no `Contents/Resources` to read, so it comes up on the base theme alone — the GUI is meant to run bundled.

### objc2 version pinning (important)

`objc2 0.5` + `objc2-foundation 0.2` + `objc2-app-kit 0.2` are a **matched set** of APIs (newer major versions exist but are intentionally not used). If a type/method fails to compile, first check whether cargo upgraded a crate out of the set (`cargo tree | grep objc2`) and whether `objc2-app-kit`'s feature list is missing an entry — that crate splits features per Objective-C class, so each `NS*` type used must be enabled as a feature in `tabt-app/Cargo.toml`.

## Bundle

`bundle/Info.plist.in` is the app manifest template (min macOS 12.0, version tracked alongside the crate versions — `make dmg` reads `CFBundleShortVersionString` back out of the built plist for the image name); the Makefile substitutes `__APP_NAME__`/`__BUNDLE_ID__`/`__EXEC__` and writes the result, plus `bundle/AppIcon.icns`, `bundle/themes.conf` (the shipped theme defaults), `bundle/Credits.rtf` (what the standard About panel shows: the blurb and the repository link, as an RTF `HYPERLINK` field) and the binary, into `<app>/Contents/`. Everything that goes into `Contents/` must be copied **before** the `codesign` step — a resource added afterwards invalidates the signature.

### Build identities

The shipped app is **TabT**; `make`/`make run` build a distinct **development** identity so both can be installed and run side by side:

| | `make` / `make run` | `make release` / `make dmg` |
|---|---|---|
| bundle | `dist/TabT Dev.app` | `dist/TabT.app` |
| bundle id | `dev.local.tabt.dev` | `dev.local.tabt` |
| executable (`ps`, `killall`) | `tabt-dev` | `tabt` |
| config dir | `~/.tabt-dev` | `~/.tabt` |

The Makefile passes `TABT_APP_NAME`/`TABT_CONFIG_DIR` to cargo; `tabt-app/src/branding.rs` reads them with `option_env!` (defaulting to the release identity, so a plain `cargo build` still yields the shipping app) and every user-visible name — window title, app menu, quit dialog, empty-pane placeholder — goes through `branding::APP_NAME`. `build.rs` declares `rerun-if-env-changed` for both, so switching identities forces a rebuild of `tabt-app`. `TERM_PROGRAM` is deliberately **not** branded: it stays `TabT` in both, since shell integrations match on it.

`bundle/AppIcon.icns` is generated from `tabt.png` — do not hand-edit it. Use the tracked `app-icon` skill (`.claude/skills/app-icon/`), which documents the non-obvious macOS icon constraints. `.gitignore` deliberately tracks `.claude/skills/` while ignoring the rest of `.claude/`.
